## PPC rules (Production Planning dashboard)
- One colour per SKU (15 Nov 2026), worked out from the data - do not trust the sheet's Auto Status when it conflicts:
  1. RED = overdue: ship date passed (first filled of Ship Date (2) → Effective Ship Date → Revised Ship Date → Ship Date) AND Ship date Actual empty. Red always wins.
  2. Otherwise the sheet's Auto Status (Purple, Yellow, Orange, Green, Light / Medium / Dark Blue).
  3. Auto Status blank or #REF! and not late → Green.
  Only one chip per SKU ("Red - overdue"; no second "Late" chip). The Late count, the Overdue Only filter and the colour counts all use this same rule, so Red count = Late count.

- 21 Nov 2026: **design-desk fixed - the other half of "the mail server is busy".** It was killing itself **578 times out of 1,433 runs** with "Memory limit exceeded" (576 of the whole project's 589 memory kills that day) on the same shared compute as Rugs Email, so it was taking other people's in-flight requests down with it. The state told the whole story: **89,427 indexed attachments (131 GB), only 180 ever copied to Drive, 89,247 waiting - and not one recorded failure.** That last number is the giveaway: a memory kill never reaches a `catch`, so nothing was ever written down and **the very next tick picked the same five files again, for ever**. Seven days of this copied 26 files a day. TWO CAUSES: (1) `fileBytes` decoded an attachment as `Uint8Array.from(atob(pad64(String(j.data))), ...)` on the result of `res.json()`, so for a 25 MB file (`FILE_BACKUP_MAX`) the raw body (~33 MB of base64), the parsed JS string (the same again at **2 bytes a character** = 66 MB) and atob's binary string (50 MB) were all live at once - **over 130 MB** on a runtime that has nothing like that to give; (2) the copy loop took **five rows at a time** and ran to its time budget, so one tick could line up several of those downloads back to back. FIXES, all inside the function: (1) new `attBytes` reads the attachment **off the response body as it arrives** and decodes each whole 4-character group, carrying a split tail over between network chunks - the only big thing in memory is the file itself; (2) **the try is written down BEFORE the file is fetched** (new column `dd_files.backup_tries`, + a partial index on the queue), so a file that still kills the run is **set aside after 3 goes** instead of blocking the queue - this is the part that breaks the crash loop; (3) one file at a time, at most `TICK_BYTES` (80 MB) a tick; (4) the files job now gets **25 s** of its own (`FILES_BUDGET_MS`) - it had been sharing the 10 s budget whose first 6 s go on the "last 3 days" scans, leaving ~4 s, i.e. **one file a run** - and `LOCK_TTL_MS` went 30 s -> 150 s, because 30 s is **shorter than a run is allowed to take**, so a perfectly healthy run was being treated as stale and a second one started on top of it.
